# 审查机制：两轮对抗审查 + 人类终审

## 第一轮：Muse 首轮审查

WorkBuddy 提 PR 后，Muse 立即审查，不等 Codex 和人类。

检查项：
1. 是否完成对应 Issue 的全部验收标准。
2. 是否符合 `docs/PLAN.md` 和 `docs/DECISIONS.md`，有没有跑偏。
3. 有没有幻觉：假实现、不存在的接口、硬编码凑数、逻辑漏洞。
4. 有没有破坏已有功能，命名、结构是否一致。
5. 提交是否干净，一个 PR 只做一件事。

结果：
- 合格：标注“首轮通过”，送 Codex 第二轮审查。
- 不合格：在 PR 里写清具体问题和要改的文件、行，直接打回重写，不用等人类。

## 第二轮：Codex 终审

Codex 只审方向、架构和验收，不做日常轮询。

检查项：
1. 架构和技术选型是否符合规划。
2. 是否可以合进 main，是否满足部署条件。
3. 有没有需要返工或拆分的地方。

结果：通过 / 打回，并写清理由。

## 最终：人类部署

只有人类能决定是否正式部署上线。Codex 和 Muse 都只有建议权，没有部署权。

## 成本原则

- Codex 额度贵，只用于规划和终审。
- Muse 负责高频检查和首轮审查。
- WorkBuddy 用低成本模型做执行，任务切小、并行跑。
